# Развёртывание с нуля на чистой системе

Проверка проведена по коду и по конфигурации, не по памяти. Критерий: человек
взял репозиторий, поднял по инструкции и получил рабочий продукт, ни о чём не
догадываясь.

**Критерий сейчас не выполняется.** Ниже что мешает, по убыванию тяжести.

## Блокеры чистого запуска

### 1. Пример окружения предлагал строку подключения, с которой compose не работает

Было: `postgresql://postgres:password@localhost:5432/tessera`.

Контейнер базы создаёт **пользователя `tessera` и базу `tessera`**
(`docker-compose.yml`, сервис `tessera-db`), а хост внутри сети compose это
имя сервиса, не `localhost`. Скопировавший пример получал отказ подключения на
старте и не имел способа догадаться, почему.

**Исправлено** в этом заходе: пример даёт рабочие для compose значения, а
вариант для запуска без docker вынесен в закомментированные строки.

### 2. Двадцать четыре переменные приложение читает, а compose не передаёт

`docker-compose.yml` **не использует `env_file`**, окружение перечисляется
поимённо. Всё, что не перечислено, до контейнера не доходит: задать это через
файл окружения невозможно, значение молча остаётся пустым.

Не передаются:

```
AI_COMPLETION_MODEL      AI_DRIVER              AI_EMBEDDING_DIMENSION
AI_EMBEDDING_MODEL       AI_EMBEDDING_SUPPORTS_MRL
CLICKHOUSE_URL           CLOUD                  COLLAB_PORT
COLLAB_SHOW_STATS        COLLAB_URL             DEBUG_DB
DEBUG_MODE               EVENT_STORE_DRIVER     GEMINI_API_KEY
HOST                     LOG_HTTP               MAIL_DRIVER
OLLAMA_API_URL           OPENAI_API_KEY         OPENAI_API_URL
PORT                     SEARCH_DRIVER          SUBDOMAIN_HOST
TRUST_PROXY_HOPS
```

Практические следствия:

- **`MAIL_DRIVER` не передаётся**, то есть выбрать способ отправки почты
  переменной окружения в docker нельзя
- **`OPENAI_API_KEY`, `GEMINI_API_KEY`, `AI_*` не передаются**. Ключи ИИ можно
  задать через интерфейс (они хранятся в базе зашифрованными), но переменными
  окружения — нельзя, хотя код их читает
- **`TRUST_PROXY_HOPS` не передаётся**. Переменная заведена в этой сессии и
  описана в `STACK.md`, но в контейнер не попадает, то есть настроить число
  доверенных прокси в docker сейчас невозможно. **Это мой недосмотр в той же
  сессии**
- `PORT`, `HOST`, `DEBUG_MODE`, `LOG_HTTP` имеют значения по умолчанию в коде,
  их отсутствие безвредно

**Не исправлено.** `docker-compose.yml` в этом проекте правится только по
явному запросу владельца: он завязан на боевое развёртывание. Список выше —
готовое задание на правку.

### 3. Инструкции по установке нет

`README.md` — 16 строк, один раздел «Features». Ни требований, ни порядка
запуска, ни слова про файл окружения.

`docs/deployment.md` описывает развёртывание на конкретный VPS через GitHub
Actions, с чужим доменом и адресом, и к чистой установке отношения не имеет.

**Исправлено** этим документом.

## Порядок первого запуска

Требуется: Linux, Docker с плагином compose. Больше ничего — Node и pnpm нужны
только для разработки, образ собирается внутри Docker.

1. Забрать репозиторий и перейти в его каталог
2. Скопировать `.env.example` в `.env`
3. Внести в `.env` ровно две обязательные правки:
   - **`APP_SECRET`** — не менее 32 символов, `openssl rand -hex 32`.
     Приложение проверяет длину на старте и отказывается запускаться
   - **`POSTGRES_PASSWORD`** — и тот же пароль внутри `DATABASE_URL`.
     Compose подставляет пустое значение, если переменной нет, и база
     поднимается настроенной неверно
4. `docker compose up -d`

Первый запуск занимает минуты: собирается образ, поднимается PostgreSQL,
Redis, MinIO, Gotenberg, Draw.io, SearXNG и внутренний сервис `tessera-hub`.

**Миграции применяются сами.** Приложение прогоняет их на старте, когда
`NODE_ENV=production`, а он задан в самой команде запуска образа
(`start:prod`), а не переменной окружения. Отдельного шага не требуется.

Готовность проверяется запросом `GET /api/health`. Ответ `{"status":"ok"}` с
разделами `database` и `redis` означает, что база и Redis подключены и
миграции прошли.

## Первая учётная запись

Заводится через интерфейс, не записью в базу. Открыть `http://localhost:3000` —
пустой экземпляр отдаёт экран настройки, который создаёт рабочее пространство
и первого владельца (`POST /auth/setup`, закрыт `SetupGuard`, работает только
пока рабочего пространства нет).

Второй раз этот путь не срабатывает. Дальнейшие люди добавляются приглашением.

## Внешние службы

### Обязательные

| Служба | Зачем | Что будет без неё |
|---|---|---|
| `tessera-db` (PostgreSQL 18 + pgvector) | всё | приложение не стартует |
| `tessera-redis` | сессии, очереди, синхронизация | приложение не стартует |

Обе перечислены в `depends_on` у приложения.

### Поднимаются compose, но приложение стартует и без них

| Служба | Зачем | Что теряется |
|---|---|---|
| `tessera-minio` | вложения | загрузка и отдача файлов |
| `tessera-gotenberg` | экспорт PDF | выгрузка в PDF |
| `tessera-drawio` | диаграммы | редактор диаграмм |
| `tessera-searxng` | веб-поиск для ИИ | ответы на вопросы о текущем |
| `tessera-hub` | версии, телеметрия, документация, лицензия | соответствующие экраны |

### Внешние по отношению к развёртыванию

Ровно две, обе необязательные:

- **провайдер модели ИИ** (OpenRouter или совместимый). Без него работает всё,
  кроме ИИ. Ключ задаётся через интерфейс, он хранится в базе зашифрованным
- **SMTP** для писем настоящим адресатам. Без него приглашения и уведомления
  не уходят

## Что известно только из переписки и нигде не записано

Ниже то, что выяснилось в работе и до этого документа нигде не фиксировалось.

1. **Имя `tessera` зашито в двух местах вне compose**: `PDF_RENDER_BASE_URL` и
   `--chromium-allow-list` у Gotenberg. Переименование сервиса ломает экспорт
   PDF. Записано в `CLAUDE.md`, но не в документации развёртывания
2. **`tessera-db` не резолвится с хоста.** Применить миграции или выполнить
   кодогенерацию с машины разработчика можно только по адресу контейнера:
   `docker inspect -f '{{range .NetworkSettings.Networks}}{{.IPAddress}}{{end}}' tessera-tessera-db-1`
3. **Dev не применяет миграции.** `pnpm dev` их не прогоняет, нужен
   `pnpm --filter server migration:up` вручную
4. **Изолированной сборке сервера нужны собранные общие пакеты**
   (`packages/base-formula/dist`, `packages/editor-ext/dist`). `pnpm build`
   порядок соблюдает сам, а `pnpm --filter server build` в чистом чекауте
   упадёт
5. **`SEARXNG_SECRET` в compose ни на что не влияет**: образ подставляет её
   правкой смонтированного только на чтение файла настроек, и подстановка не
   проходит
6. **После каждой сборки образа надо убирать старое.** Каждая пересборка
   оставляет образ без тега, за сутки работы это десятки гигабайт. Записано в
   `CLAUDE.md`
7. **На машине с несколькими проектами** имена сервисов и `container_name`
   обязаны нести префикс проекта, иначе `docker compose down` снесёт чужой
   контейнер
8. **Приложение должно быть доступно только через обратный прокси**, иначе
   защита адреса клиента от подстановки заголовком не работает. Записано в
   `docs/deployment.md`

## Что осталось непроверенным

**Чистый запуск на чистой системе не воспроизводился.** Проверка проведена
чтением конфигурации и кода: сверкой переменных, читаемых приложением, с
переданными в compose и перечисленными в примере. Настоящий прогон на пустой
машине потребовал бы отдельного стенда, которого здесь нет. Это ограничение, а
не вывод.
