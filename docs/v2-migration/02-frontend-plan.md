# Фронтенд v2

## Оговорка о шаблоне

Задание отсылает к `claude-template-svelte/`. **Каталога в этом окружении
нет.** Решения ниже выведены из целевого стека, а не из шаблона, и подлежат
сверке с ним.

## Adapter

**Рекомендация: `adapter-node`.**

Обоснование: продукт разворачивается своим docker compose за nginx, статики
одного бандла недостаточно (нужны прокси на `/api`, `/socket.io`, `/collab`),
а платформенные адаптеры (Vercel, Netlify) к этому способу развёртывания
отношения не имеют. `adapter-static` не подходит: часть маршрутов требует
серверной отдачи и переменных окружения на старте, как сейчас делает
`StaticModule`.

## Роутинг

43 страницы v1 ложатся на файловый роутинг SvelteKit. Группы:

```
routes/
  (auth)/login, signup, invite, forgot-password, password-reset
  (app)/s/[spaceSlug]/p/[pageSlug]      страница
  (app)/s/[spaceSlug]                    пространство
  (app)/home, search, settings/...       рабочие экраны
  (share)/share/[shareId]                публичный доступ
  ai/chat/[chatId]                       чат
```

`+layout.svelte` на группу вместо нынешних layout-компонентов.

## Состояние

Svelte 5, **режим runes обязателен**. `$state`, `$derived`, `$effect`.
`svelte/store` и `export let` не используются.

Нынешние 5 файлов с атомами Jotai переносятся в runes-модули. Объём небольшой:
состояние в v1 в основном живёт в TanStack Query, а не в атомах.

## Работа с API

Порядок из v1 переносится: **компонент не вызывает HTTP напрямую**.
`features/<домен>/types` → `services` → `queries` → компонент.

TanStack Query имеет сборку для Svelte, кеш и инвалидация переносятся один в
один. Это существенно: инвалидация в v1 уже выверена, и переписывать её логику
заново не нужно.

## Темы

Tailwind 4 через `@import` в `app.css`. Тёмная и светлая тема через
`data-theme` на корне, как сейчас.

## i18n

12 локалей, 1 991 ключ. **Ключ — английская фраза**, это правило переносится.

Библиотека: `sveltekit-i18n` или `typesafe-i18n`. Требования к ней из практики
v1:

- поддержка форм множественного числа для славянских языков (`few`, `many`)
- отсутствие синтаксиса ICU (в v1 его нет и заводить не надо)
- подстановка вида `{{name}}`

**Проверки словарей переносятся все три**, они окупились: каждый ключ из кода
заведён в источнике; текст уведомления не задаётся строкой мимо перевода;
строка справочника (`message`, `label`, `title`, `description`) заведена в
источнике.

## Конвенции из шаблона проекта

Источник: `__temp__/claude-templates/claude-template-svelte`. Шаблон описывает,
как в этих проектах принято писать на SvelteKit, и расходиться с ним без повода
не надо.

- Svelte 5 в режиме рун везде: `$state`, `$derived`, `$effect`, `$props`.
  Старые хранилища из `svelte/store` и `export let` не применяются.
- TypeScript в строгом режиме. Свойства объявляются типом `type Props = {...}`
  и разбираются одним `$props()`.
- Ввод-вывод только по краям: `fetch`, `localStorage`, `window` — в `onMount` и
  `onDestroy`. Побочное действие в `$effect`, а не в `$derived`.
- Компоненты лежат в `src/lib/components/<группа>/<Name>.svelte`, у корня
  каждого `data-component="<Name>"`, у крупных секций `data-section`, у
  маршрутов `data-route`. Это опора для проверки глазами через браузерный MCP.
- Состояние — классы в `src/lib/stores/<name>.svelte.ts`.
- Темы через `data-theme` на `html` плюс переменные CSS в `app.css`, значение
  выбирается скриптом в `app.html` до отрисовки, иначе видна вспышка. Цвета в
  компонентах не хардкодятся.
- Словари в `src/lib/i18n/locales/<locale>.json`, каждый ключ обязан быть во
  всех языках.
- Клиент API в `src/lib/api/client.ts`.
- Источник истины по стилям — отдельный `STYLES.md`, по стеку — `STACK.md`.

### Два расхождения, которые надо решить до первой строки

**Пакетный менеджер.** Шаблон написан под `npm`, а Tessera это монорепо на
`pnpm` с рабочими пространствами. Заводить второй менеджер в одном репозитории
нельзя: два файла блокировок на один `node_modules` дают разные деревья у
разных людей. Берётся `pnpm`, команды из шаблона читаются с поправкой на него.

**Комментарии в коде.** Шаблон требует писать без комментариев, если их не
попросили. В серверной части этого проекта правило обратное: комментарий
объясняет неочевидное, и такие комментарии там ценны. Расхождение не мнимое —
на фронте разметка и стили обычно говорят сами за себя, а неочевидное там
другое: порядок эффектов, обход всплытия, обходы поведения браузера. Правило
для фронта принимается такое: без комментариев по умолчанию, но с
комментарием там, где поведение не выводится из кода, — то есть как в
серверной части, только повода возникают реже.
