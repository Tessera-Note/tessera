# Как проверяется результат

## Три уровня, и что относится к каждому

### Тестами

- бизнес-правила сервисов, ветки исключений, права доступа
- разбор и сборка данных: SCIM-фильтры, схемы API, преобразование содержимого
- каждая новая публичная функция, каждая новая ветка

**Правило из v1 переносится: проверка, которая смотрит на текст исходников
вместо поведения, негодна.** Если проверяемое свойство выражается в чём-то
исполнимом, проверять надо исполнимое: SQL — компиляцией запроса, декораторы —
метаданными, конфигурацию — импортом константы.

**И второе правило: сторожевую проверку проверять внесением дефекта.** Зелёная
проверка не доказывает, что она что-то ловит. В v1 за одну сессию три
написанные проверки оказались негодными, и все три были зелёными. Возвращать
исходник после мутации копией файла, а не `git checkout`: откат унесёт
незакоммиченную правку вместе с мутацией.

### Сверкой с v1

Пока обе версии работают на одной базе, доступна проверка, которой не будет
потом: **одинаковый запрос к v1 и v2 должен давать одинаковый ответ**.

Это основной инструмент фаз 1 и 2. Для 248 маршрутов сверка автоматизируется:
список запросов, прогон против обеих версий, дифф ответов. Расхождение —
дефект, пока не доказано обратное.

### Живой проверкой человеком

Что не проверяется автоматически и требует глаз:

- **редактор**: 38 представлений узлов, каждое создать, изменить, сохранить,
  открыть в v1
- **совместное редактирование**: двое в одной странице, разрыв соединения
- **экспорт**: PDF и DOCX открываются в Word и в просмотрщике, вёрстка сравнима
- **импорт**: настоящие выгрузки Google Docs и Confluence
- **вход через провайдера**: настоящие OIDC, SAML, LDAP
- **внешний вид**: 505 компонентов на новой библиотеке

## Обязательное после сборки образа

Из практики v1:

- **проверять старт контейнера, а не только сборку.** Правка конструктора или
  списка `imports` модуля собирается зелёной и падает на старте
- **подтверждать факт развёртывания**, а не предполагать: образ несёт правку,
  здоровье отвечает, исключений при старте нет
- **убирать за собой**: кеш сборки безусловно, старые образы по перечислению
  идентификаторов с проверкой владения

## Пост-скоуп ревью

После каждого закрытого куска, до слова «готово»: поиск заглушек, доменный
ревьюер по месту правки, поиск того же класса дефекта по всему коду, проверка
покрытия новых веток, полный прогон.

**Самый важный шаг — третий.** Один класс правки почти всегда встречается
больше одного раза.
