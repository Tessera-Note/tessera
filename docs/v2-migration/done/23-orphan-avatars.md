# 23. Аватары-сироты при удалении участника

Пункт не из чек-листа. Он пришёл из `docs/future-roadmap.md`, где было записано
условие: «когда удаление пространства или участника будет перенесено, уборка
вложений переносится **той же задачей**».

## Было

В v1 уборка вложений — четыре обработчика очереди: страницы, пространства,
участника и беседы с ИИ.

В v2 на момент проверки было закрыто два случая: вложения страницы убираются
при безвозвратном удалении из корзины (`services/maintenance.py`), прежний
аватар и логотип — при замене (`AttachmentService.upload_image`).

Раздел документа отложенного утверждал, что остальных обработчиков нет
намеренно, потому что «маршрутов удаления пространства и удаления участника в
v2 не существует вовсе». Это перестало быть правдой: `api/spaces.py` держит
`POST /delete`, `api/workspace.py` — `POST /members/delete`.

Удаление участника обезличивает его строку одним запросом, и в числе прочего
проставляет `avatar_url = NULL`. Файл при этом остаётся в хранилище: имя
случайное, владельца уже нет, ни отказа, ни записи в журнале — обнаружить его
потом не по чему.

## Сделано

`WorkspaceService.delete_member` запоминает адрес аватара до обезличивания и
после фиксации вызывает `_forget_avatar` (`services/workspace.py`). Метод
собирает ключ тем же `image_key`, каким аватар клался, убирает файл из
хранилища и снимает учётную строку вложения.

Порядок тот же, что при замене: сначала снята ссылка, потом убран файл.
Обратный порядок при сбое оставил бы ссылку на несуществующий файл, то есть
битую картинку вместо прежней.

Отказ хранилища не отменяет удаление участника. Человек к этому моменту уже
удалён, откатывать нечего, и попытка отката была бы хуже: она вернула бы
удалённого. Отказ уходит в журнал предупреждением, файл остаётся до ручной
уборки.

Внешний адрес (`http://`, `https://`) пропускается: он не наш, удалять по нему
нечего, а `image_key` собрал бы из него бессмысленный ключ.

Хранилище приходит в `WorkspaceService` необязательным доводом: остальные его
вызовы (`api/auth.py`, `api/workspace.py` в прочих маршрутах) хранилища не
касаются, и требовать его от них значило бы тянуть зависимость через весь файл
ради одного метода. Маршрут `/members/delete` получает `Storage` через тот же
`NamedDependency`, каким его получают вложения.

Удаление пространства отдельного обработчика не требует, и это проверено.
Удаление мягкое: `SpaceService.delete` проставляет отметку самому пространству
и его страницам, а тот же проход по корзине (`services/maintenance.py`) убирает
их вложения позже, вместе со страницами.

Четвёртый обработчик v1, уборка вложений беседы с ИИ, мёртв и в самой v1:
задание не ставится нигде, а `AiChatService.deleteChat` только помечает беседу
удалённой. Вложений вида `chat` в v2 никто не создаёт. Переносить его как
рабочий код нельзя — это была бы заглушка.

Раздел в `docs/future-roadmap.md` приведён в соответствие с кодом: из него
убрано всё, что теперь сделано, и осталась только та часть, которую переносить
запрещено.

## Проверено

Две проверки в `tests/test_workspace_settings.py`:
`test_the_avatar_leaves_the_storage_with_its_owner` — файл ушёл из хранилища и
учётная строка снята; `test_an_external_avatar_is_left_alone` — по внешнему
адресу хранилище не трогали.

Обе проверены мутацией на восстановленном файле: снятие вызова `_forget_avatar`
роняет первую, снятие проверки на внешний адрес — вторую. Каждый раз падала
ровно одна из тридцати одной.

Полный прогон `apps/api`: 1903 проверки, `ruff` чист.
