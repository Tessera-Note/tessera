# 28. Обратный прогон схемы

Запись без пункта чек-листа: требование стояло в `../03-data-and-migrations.md`
как невыполненное — «полный обратный прогон (чистая база, `baseline.sql`, затем
Atlas, затем сравнение с рабочей) **не выполнялся**». Прогон стал возможен,
когда у второй версии появилась своя база в составе compose
(`27-local-deployment.md`).

## Было

Схема второй версии держится на двух средствах: Atlas ведёт таблицы
декларативно, всё прочее — расширения, функции, настройка поиска, триггеры —
ведётся обычным SQL, снятым с рабочей базы. Порядок был записан так: сначала
`baseline.sql`, потом Atlas. Проверить его было не на чем: чистой базы не было,
а удаление баз в этом окружении закрыто защитным правилом.

## Сделано

Прогон выполнен: чистая база, `baseline.sql`, Atlas, `after-atlas.sql`, затем
снимок схемы по пяти срезам — колонки, индексы, ограничения, триггеры, функции —
и сравнение с рабочей базой. По 1339 строк с каждой стороны.

**Порядок оказался неверен.** Триггеры лежали в `baseline.sql`, то есть
применялись до таблиц. На чистой базе применение падало на первом же:
`relation "public.ai_chat_messages" does not exist`. Триггеры вынесены в
`after-atlas.sql` — файл, который применяется после Atlas.

**Atlas не видит `COLLATE` у колонки индекса.** Четыре индекса по ключу порядка
(`idx_pages_space_parent_position`, `idx_pages_is_base`,
`idx_base_rows_page_alive`, `idx_base_properties_page_alive`) созданы в рабочей
базе с `COLLATE "C"`. Замерено обоими концами: `schema inspect` рабочей базы
отдаёт их без сортировки, `schema apply` создаёт их без неё же. Ни отказа, ни
предупреждения — разница видна только в сравнении снимков.

Индексы вынесены в `after-atlas.sql` и **исключены** из ведения Atlas
(`--exclude`). Без исключений он удалял их при каждом применении как лишние, а
следующий шаг создавал заново: на своей машине это лишняя перестройка, на общей
с v1 базе — перестройка рабочих индексов с блокировкой, молча.

**Оставшееся расхождение — не расхождение.** Ограничение
`groups_directory_source_check` записано в двух базах разными скобками:
`ANY (ARRAY[...]::text[])` против `ANY (ARRAY[...::text, ...::text])`. Так
Postgres печатает выражение в зависимости от того, как его создали. Проверено
поведением, а не чтением: обе базы отвергают значение вне списка тем же именем
ограничения и принимают `scim`.

## Проверено

Сравнение снимков: 1339 строк с каждой стороны, расхождение одно и разобрано
выше. Повторный подъём состава: «Schema is synced, no changes to be made», все
четыре индекса с сортировкой на месте.

Косвенно — работой: поиск на поднятом развёртывании находит набранную фразу, а
это разом проверяет настройку `tessera_search`, функцию `f_unaccent` и триггер
`pages_tsvector_update`.

## Замечено попутно, не исправлено

Сортировка `C` у этих индексов не совпадает с сортировкой самих колонок: у
`position` она по умолчанию базы (`en_US.utf8`), а приложение сортирует обычным
`ORDER BY position`, без указания сортировки. План это подтверждает — индекс не
используется для упорядочивания, планировщик ставит `Sort`. То есть индексы в
их нынешнем виде порядок не ускоряют.

Это свойство v1, перенесённое в v2 дословно и сознательно: обе версии работают
с одной базой, и расхождение определений индекса означало бы разные планы у
одинаковых запросов. Менять — отдельное решение, оно записано в
`../../future-roadmap.md`.
