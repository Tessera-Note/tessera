# Tessera

Совместная вики: рабочие пространства содержат spaces, spaces содержат иерархические страницы с правами, комментариями, вложениями, историей, поиском и совместным редактированием в реальном времени. Форк Docmost 0.95.0, монорепо Nx + pnpm.

Экземпляр разворачивается через docker compose и работает без обращений в интернет. Все вспомогательные сервисы подняты рядом: `tessera-hub` (версии, телеметрия, документация, лицензия, поддержка), `tessera-drawio` (диаграммы), `tessera-minio` (вложения), `tessera-gotenberg` (экспорт PDF), PostgreSQL и Redis. Осознанные исключения ровно два: провайдер модели для ИИ (OpenRouter) и внешний SMTP для писем реальным адресатам.

Новая внешняя зависимость в рантайме запрещена. Если возможности не хватает, поднимается сервис в compose, а недостающий код пишется на Python и Litestar по образцу `services/hub`.

Из этого правила есть одно исключение, и оно закрытое: `services/collab` на Node. Там живут схема узлов редактора (расширения Tiptap) и протокол Hocuspocus, и второе их описание на Python теряло бы узлы документа молча, без единого отказа. Исключение ограничено этим сервисом и этими двумя предметами: решения о правах и запись в базу остаются на Python, сосед спрашивает их внутренними маршрутами `/api/internal/collab/*`. Распространять исключение на другие подсистемы запрещено.

Внешних git-сабмодулей в репозитории нет. Каталог `apps/server/src/ee` это обычный каталог, его код принадлежит проекту и правится наравне с остальным. Подключать чужие репозитории сабмодулями запрещено.

Стек, версии, конфиги, команды и переменные окружения в `@STACK.md`.
Тематический контекст по слоям в `@docs/ai-context/README.md`, там таблица «задача - какие файлы читать».
Универсальные соглашения в `@PROJECT_GUIDELINES.md`. При расхождении приоритет у этого файла, он отражает специфику проекта.
Английская версия рабочих правил в `@AGENTS.md`, она остается для внешних агентов, дублировать ее сюда не надо.
Отложенные доработки и отсутствующие модули в `@docs/future-roadmap.md`. Это единственное место для отложенных задач, реализованный пункт оттуда удаляется.

## Язык общения

Отвечать на русском. Тон формальный, профессиональный. Без эмодзи, без капслока, без маркетинговых формулировок.

Комментарии и строки в коде остаются на языке файла, который правишь. Пользовательские тексты только через i18next.

## Главное правило

Для нетривиальных правок (более одного файла или больше 50 строк) сначала описание бизнес-логики и вариантов решения с обоснованием, реализация после подтверждения. Для точечных однофайловых правок можно сразу код.

При множественных правках одного файла возвращать полный файл.

## Режим работы

Компромисс смещен в сторону осторожности, а не скорости.

- формулировать допущения явно, при неуверенности спрашивать
- при нескольких интерпретациях представлять их, не выбирать молча
- при наличии более простого подхода сообщать об этом
- если что-то неясно, останавливаться и называть конкретно что

Точечные изменения. Менять только то, что необходимо. Не улучшать соседний код, не рефакторить то, что не сломано. Осиротевшие из-за твоих правок импорты и переменные убирать. Не связанный с задачей мертвый код упоминать, но не удалять.

Временные решения (`TODO`, `FIXME`, отладочный `console.log`, заглушки, `throw new Error('not implemented')`) запрещены в production коде. Если задача требует стаба, значит задача не готова к реализации.

## Post-Release Policy

Кодовая база стабилизирована и работает в продакшене. Применять постоянно.

- только фиксы и точечные улучшения, без крупных рефакторингов
- минимальные диффы, изменения строго в границах задачи
- не переименовывать переменные, не переставлять функции, не чистить соседний код
- существующие комментарии не удалять и не переписывать, если фикс не меняет описанное поведение. В этом репо комментарии объясняют неочевидное (исключение `api/mcp` из глобального префикса в `apps/server/src/main.ts`, `chromium-allow-list` в `docker-compose.yml`), они ценны
- в новом коде комментарии писать только там, где поведение неочевидно из кода
- не менять тестовую инфраструктуру (`apps/server/test/`, моки, фикстуры), если этого не требует фикс
- новый и измененный код обязан иметь тесты на каждую новую ветку

## Архитектурные ограничения

- сохранять существующую архитектуру, переиспользование существующего кода в приоритете
- не менять входные и выходные параметры публичных функций и DTO без согласования
- не предлагать архитектурные модификации без запроса
- решать первопричины, а не симптомы, без обходных путей

Границы, которые нельзя размывать.

- `apps/server/src/core` это бизнес-логика. Не тянуть в нее детали storage, mail, redis, очередей напрямую, когда есть модуль в `apps/server/src/integrations`
- контроллер держит маршрут, статус, guard и извлечение контекста. Бизнес-правила в сервисе, запросы Kysely в репозитории `apps/server/src/database/repos`
- новый бизнес-модуль регистрируется в `apps/server/src/core/core.module.ts`, инфраструктурный в `apps/server/src/app.module.ts`
- на клиенте компонент не вызывает axios напрямую. Порядок `features/<домен>/types` - `services` - `queries` - компонент
- `apps/server/src/collaboration` (Hocuspocus/Yjs, ws `/collab`) и `apps/server/src/ws` (Socket.IO) это два разных канала. Не подменять один другим

## Уборка после сборки

Каждая пересборка образа оставляет предыдущий без тега, плюс растет кеш сборки.
За сутки работы это набирает десятки гигабайт и упирается в диск.

После каждой сборки образа убирать старое:

```
docker builder prune -f
docker images -f dangling=true
```

Кеш сборки чистится безусловно, он регенерируется. Образы без тега удалять
только перечислением конкретных идентификаторов и только после двух проверок:
образ не занят контейнером (`docker ps -a --format '{{.Image}}'`) и метка
`com.docker.compose.project` у него `tessera`. На этой машине несколько
проектов, и часть чужих контейнеров держит образы по идентификатору, без тега.

Тома не трогать никогда: под ними базы, MinIO и Redis всех проектов.
`docker system prune` и любые маски в командах удаления не применять.

## Что не трогать

Под запретом без явной команды пользователя.

- `apps/server/src/database/migrations/` существующие файлы. Даже если в миграции баг, создается новая миграция
- `apps/server/src/database/types/db.d.ts`, генерируется через `pnpm --filter server migration:codegen`
- `pnpm-lock.yaml`, регенерируется пакетным менеджером
- `patches/`, генерируется `pnpm patch`
- `node_modules/`, `dist/`, `apps/client/dist/`, `.nx/`
- `.env` на запись и модификацию. Чтение разрешено для диагностики подключений к базе и Redis, содержимое не выводить в чат и не коммитить
- `docker-compose.yml`, `deploy/docker-compose.vps.yml` и `Dockerfile` без явного запроса, они завязаны на продакшен деплой
- переименование сервисов в существующих compose-файлах. Имя `tessera` зашито в `PDF_RENDER_BASE_URL` и в `--chromium-allow-list` у Gotenberg, переименование ломает экспорт PDF
- сигнатуры публичных API, DTO, схемы стора и типы внешнего API

## Команды проверки

Node 22, pnpm 10.18.3. Установка `pnpm install --frozen-lockfile`.

| Команда | Что делает |
|---|---|
| `pnpm dev` | клиент и сервер вместе, сервер на 3000, Vite проксирует `/api`, `/socket.io`, `/collab` на `APP_URL` |
| `pnpm build` | полная сборка Nx в порядке зависимостей |
| `pnpm --filter client build` | `tsc` затем сборка Vite |
| `pnpm --filter client lint` | ESLint без автофикса |
| `pnpm --filter client test -- <путь>` | Vitest, jsdom |
| `pnpm --filter server build` | nest build |
| `pnpm --filter server lint` | ESLint с `--fix`, меняет файлы |
| `pnpm --filter server test -- <путь>` | Jest, `src/**/*.spec.ts` |
| `pnpm --filter server test:e2e` | Supertest, `test/*.e2e-spec.ts` |
| `pnpm --filter server migration:up` | применить миграции, dev сам их не применяет |
| `uv run pytest` в `services/hub` | тесты внутреннего сервиса |
| `uv run ruff check .` в `services/hub` | линт внутреннего сервиса |
| `uv run alembic upgrade head` в `services/hub` | миграции базы `tessera_hub` |

Перед объявлением задачи завершенной прогнать сборку и тесты затронутого пакета. Красных тестов в финальном отчете быть не должно.

Изолированной сборке сервера нужны `packages/base-formula/dist` и `packages/editor-ext/dist`. Если их нет, сначала `pnpm --filter @tessera/base-formula build` и `pnpm --filter @tessera/editor-ext build`. `pnpm build` порядок соблюдает сам.

В текущем чекауте нет `node_modules` и нет `.git`, а `.github/workflows` отсутствует. CI, описанный в `docs/ai-context/verification-operations.md`, здесь недоступен, проверять локально.

## Пост-скоуп ревью, обязательно

После завершения любого scope и до слова «готово» прогнать чек-лист.

1. `stub-hunter` по измененным production-файлам. Найденные TODO, FIXME, отладочный console.log, заглушки это блокер
2. Доменный ревьюер, если применимо. `schema-reviewer` при правке миграций, репозиториев или типов базы. `i18n-reviewer` при правке словарей или пользовательских текстов
3. Pattern-grep того же класса бага по всему репо. Самый важный шаг. Если чинил конкретный класс проблемы (отсутствующая проверка доступа, забытая инвалидация кеша, гонка, отсутствие идемпотентности), найти остальные места с тем же паттерном. В этом репо один класс правки почти всегда встречается и в HTTP, и в MCP, и в Socket.IO, и в коллаборации
4. Test coverage gap. Для каждой новой публичной функции, ветки и пути исключения проверить наличие теста. Нет теста, добавить в этой же сессии
5. Lint и полный прогон тестов затронутого пакета

Критичные находки (тот же класс бага в другом месте, нерабочий тест, рассинхрон схемы, стаб в продакшене) чинить в этой же сессии. Некритичные упомянуть в отчете и не править без подтверждения.

В финале ответа блок «Пост-скоуп ревью» с результатом по пяти пунктам. Неприменимые шаги помечать явно как неприменимые, не пропускать молча.

Подробности в `.claude/skills/post-scope-review/SKILL.md`.

## Обновление контекста

`docs/ai-context/` обязателен к поддержанию. Если изменение затронуло поведение, архитектуру, границу модуля, команду, конфигурацию или повторяющийся паттерн, обновить соответствующий тематический файл в этой же задаче и указать это в финальном ответе. Если ничего из перечисленного не менялось, сказать об этом явно.

Не копировать туда большие блоки кода, полные списки эндпоинтов и планы задач. Только проверяемые факты и пути в коде.

Структуру проекта и раздел команд в этом файле обновлять при появлении новых директорий, пакетов и скриптов.

## Безопасность

- никогда не логировать JWT, `APP_SECRET`, ключи API провайдеров ИИ, пароли SMTP, токены Stripe и SCIM
- ключи провайдеров ИИ хранятся шифрованными (AES-256-GCM от `APP_SECRET`), наружу отдается только маскированный превью. Не добавлять пути, которые вернут ключ целиком
- новый эндпоинт под `/ai`, `/mcp` или `/pdf-export` обязан получить тот же throttling guard, глобального лимита на них нет
- любая новая выдача содержимого страницы обязана пройти `PageAccessService` или `PagePermissionRepo`, а не только проверку членства в space
- `@Public()` это изменение поверхности аутентификации. Ставить только осознанно и объяснять в ответе
- секреты не выкладывать в чат, коммиты и документацию

## Docker

При создании новых compose-файлов и при добавлении новых сервисов в существующие имена сервисов и `container_name` обязаны включать префикс проекта (`tessera-postgres`, `tessera-redis`, `tessera-api`). Голые имена `postgres`, `redis`, `db`, `api`, `web` не использовать, иначе на машине с несколькими проектами второй проект не поднимется или `docker compose down` снесет чужой контейнер.

Существующие сервисы `tessera`, `db`, `redis`, `gotenberg` не переименовывать, см. раздел «Что не трогать».

## Инструменты

- Chrome DevTools MCP для отладки клиента, сетевых запросов, computed styles, performance
- Context7 MCP для актуальной документации библиотек

После UI-правок при наличии браузерного MCP запустить `pnpm dev`, открыть страницу, прокликать сценарий и приложить скриншот. Не отчитываться «готово», если не убедился глазами. Typecheck и тесты проверяют код, а не функцию. Если проверить функцию невозможно, сказать об этом прямо.

Вход не через форму — сеанс выдаётся `scripts/stand-session.py`, cookie ставит `scripts/stand-cookie.py`; порядок и оговорки в `docs/ai-context/verification-operations.md`.
