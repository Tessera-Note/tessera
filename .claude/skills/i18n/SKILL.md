# Локализация

## Когда применять

В интерфейс добавляется или меняется текст, который видит пользователь. Либо надо понять, откуда берутся переводы и почему в одном языке строка есть, а в другом нет.

## Устройство

- движок i18next, настройка в `apps/client/src/i18n.ts`, словари грузятся по HTTP
- файлы `apps/client/public/locales/<locale>/translation.json`
- fallback `en-US`, режим `load: 'currentOnly'`
- 12 локалей: `de-DE`, `en-US`, `es-ES`, `fr-FR`, `it-IT`, `ja-JP`, `ko-KR`, `nl-NL`, `pt-BR`, `ru-RU`, `uk-UA`, `zh-CN`

## Главное отличие от привычной схемы

Словарь плоский, namespace нет, а ключ это английская фраза целиком.

```json
{
  "Add members": "Добавить участников",
  "Are you sure you want to delete this group?": "Вы уверены, что хотите удалить эту группу?"
}
```

В `en-US` ключ и значение совпадают. Ключей вида `group.deleteConfirmTitle` здесь нет, придумывать их не надо.

## Добавление текста

```tsx
import { useTranslation } from "react-i18next";

const { t } = useTranslation();
<Button>{t("Add members")}</Button>
```

1. Написать фразу на английском прямо в вызове `t()`
2. Добавить ту же фразу как ключ и значение в `apps/client/public/locales/en-US/translation.json`, сохраняя алфавитный порядок соседних ключей
3. Во второй версии перевести ключ во всех двенадцати словарях сразу: Crowdin выключен (см. `crowdin.yml`), наполнять их больше некому, а непереведённый ключ виден человеку английской фразой. В первой версии остальные локали не трогать — ветка `main` оставлена ретро-веткой
4. Пока перевода нет, пользователь увидит английскую фразу, а не пустоту. Это штатное поведение fallback

## Подстановка значений

Формат i18next с двойными фигурными скобками.

```json
{ "Deleted {{count}} pages": "Удалено страниц: {{count}}" }
```

```tsx
t("Deleted {{count}} pages", { count: pages.length })
```

Одинарные скобки `{count}` движок не подставит.

## Правила

- ключ обязан присутствовать в `en-US`, иначе на экране появится сырой ключ
- не-английские словари второй версии правятся напрямую, и это единственный способ их пополнить: синхронизация выключена, перезаписывать правку нечему. Наборы ключей во всех двенадцати обязаны совпадать, это проверяет `apps/web/src/lib/i18n/dictionaries.test.ts`
- одна и та же фраза не заводится под двумя ключами
- числа и даты форматируются через `Intl.NumberFormat` и `Intl.DateTimeFormat`, а не переводом в словаре
- язык не используется как признак в логике. Условие вида `if (lang === 'ru')` это сигнал неверного решения
- технические строки не переводятся: имена CSS-классов, атрибуты `data-*`, ключи запросов, значения перечислений, сообщения `console.error`

## Где лежат словари

Вторая версия (активная работа): `apps/web/static/locales/<locale>.json`, один файл на локаль, 2318 ключей у десяти локалей и 2336 у `ru-RU` и `uk-UA` — разница это славянские формы `_few` и `_many`. Множественные ключи заводятся формами `_one`/`_other` (и `_few`/`_many` для славянских), базового ключа у них не бывает: `translate()` при числовом `count` идёт сразу в форму.

Первая версия (ретро-ветка `main`): `apps/client/public/locales/<locale>/translation.json`, `en-US` и `pt-BR` по 1338 ключей, `ru-RU` и `uk-UA` по 1291. Отставание там так и останется, новых строк в ветке не появляется.

## Письма

Письма сервера собираются отдельно, шаблоны React в `apps/server/src/integrations/transactional/emails`. Это не i18next, правила выше на них не распространяются.

## Проверка

```
node -e "JSON.parse(require('fs').readFileSync('apps/client/public/locales/en-US/translation.json','utf8')); console.log('en-US ok')"
```

Затем агент `i18n-reviewer`. Он сверит ключи из кода со словарем, найдет захардкоженные тексты и сломанную подстановку.

## Антипаттерны

- ключ в стиле `namespace.camelCase`
- добавление ключа только в `ru-RU`, минуя `en-US`
- массовая правка словарей через `sed` без последующей проверки структуры JSON
- пустое значение `"ключ": ""`
- машинный перевод сразу в 12 файлов
