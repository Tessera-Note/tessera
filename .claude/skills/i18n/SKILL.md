# Локализация

## Когда применять

В интерфейс добавляется или меняется текст, который видит пользователь. Либо надо понять, откуда берутся переводы и почему в одном языке строка есть, а в другом нет.

## Устройство

- словари `apps/web/static/locales/<locale>.json`, один файл на локаль
- библиотеки нет: загрузка, подстановка и формы числа живут в `apps/web/src/lib/i18n/index.ts`
- запасной язык `en-US`
- 12 локалей: `de-DE`, `en-US`, `es-ES`, `fr-FR`, `it-IT`, `ja-JP`, `ko-KR`, `nl-NL`, `pt-BR`, `ru-RU`, `uk-UA`, `zh-CN`

## Главное отличие от привычной схемы

Словарь плоский, namespace нет, а ключ это английская фраза целиком.

```json
{
  "Add members": "Добавить участников",
  "Are you sure you want to delete this group?": "Вы уверены, что хотите удалить эту группу?"
}
```

В `en-US` ключ и значение совпадают. Ключей вида `group.deleteConfirmTitle` здесь нет, придумывать их не надо. Исключение одно — коды отказов (`error.*`), они приходят с сервера.

## Добавление текста

```svelte
<script lang="ts">
  import { locale } from '$lib/stores/i18n.svelte';
  const t = $derived(locale.t);
</script>

<Button>{t('Add members')}</Button>
```

1. Написать фразу на английском прямо в вызове `t()`
2. Добавить ту же фразу как ключ и значение в `en-US.json`, сохраняя порядок соседних ключей
3. Перевести ключ **во всех двенадцати словарях сразу**: синхронизация выключена (`crowdin.yml`), наполнять их больше некому, а непереведённый ключ виден человеку английской фразой
4. Прогнать `pnpm --filter @tessera/web test -- dictionaries`: наборы ключей обязаны совпадать

## Подстановка значений

Двойные фигурные скобки. Неизвестное имя остаётся видимым, а не превращается в пустоту.

```json
{ "Deleted {{count}} pages": "Удалено страниц: {{count}}" }
```

```ts
t('Deleted {{count}} pages', { count: pages.length })
```

Одинарные скобки `{count}` подстановка не увидит.

## Формы числа

Если в значениях есть числовой `count`, перевод идёт **сразу в форму**, а базовый ключ не используется.

- форму выбирает `Intl.PluralRules` по правилам языка, а не самодельный расчёт
- английские и прочие: `_one`, `_other`; у `ja-JP`, `ko-KR`, `zh-CN` обе формы одинаковые; во французском и португальском ноль идёт в `_one`
- славянские (`ru-RU`, `uk-UA`): `_one`, `_few`, `_many` и `_other` — последняя для дробных чисел («1,5 файла»); проверка словарей требует все четыре

```json
{
  "{{count}} pages_one": "{{count}} страница",
  "{{count}} pages_few": "{{count}} страницы",
  "{{count}} pages_many": "{{count}} страниц",
  "{{count}} pages_other": "{{count}} страницы"
}
```

Заводя множественный ключ, завести **все** формы своего языка, а базовый ключ без суффикса не заводить: при числе он не читается. `_few` и `_many` у остальных языков не используются.

## Коды отказов

Сервер не присылает готовый текст. Он присылает код (`error.auth.session_expired`), а разворачивает его словарь.

Ловушка: **код не должен оканчиваться суффиксом формы числа** (`_one`, `_few`, `_many`, `_other`) — разбор примет хвост за форму и перевода не найдёт.

Новый код заводится в `apps/api/tessera_api/domain/errors.py` и в двенадцати словарях. Соответствие проверяет `apps/web/src/lib/i18n/error-codes.test.ts`.

## Правила

- ключ обязан присутствовать в `en-US`, иначе на экране появится сырой ключ
- ключ без кода не заводится и не остаётся: обратная сверка ищет его в коде целой строкой в кавычках (кусок чужой строки не засчитывается), а ключ-слово со строчной буквы (`days`, `member`) — только доводом перевода, `t('days')` или `translate('days')`, потому что такие слова совпадают со значениями в коде
- наборы ключей во всех двенадцати словарях обязаны совпадать
- одна и та же фраза не заводится под двумя ключами
- числа и даты форматируются через `Intl.NumberFormat` и `Intl.DateTimeFormat`, а не переводом в словаре
- язык не используется как признак в логике. Условие вида `if (lang === 'ru')` это сигнал неверного решения
- технические строки не переводятся: имена классов, атрибуты `data-*`, значения перечислений, сообщения для разработчика

## Письма

Письма собираются на стороне приложения, где словарей экранов нет. У них свой каталог той же формы: `apps/api/tessera_api/infrastructure/mail_text.py`, те же двенадцать языков, те же двойные скобки, английский как запасной.

Правя письмо, править каталог писем, а не словарь экранов.

Отдельная оговорка оттуда: слово о виде доступа подставляется в предложение, и каждый язык строит предложение под себя. Переводить такие ключи в отрыве от предложения нельзя.

## Проверка

```
pnpm --filter @tessera/web test -- dictionaries
pnpm --filter @tessera/web test -- error-codes
```

Затем агент `i18n-reviewer`. Он сверит ключи из кода со словарём, найдёт захардкоженные тексты и сломанную подстановку.

## Антипаттерны

- ключ в стиле `namespace.camelCase` для обычного текста
- добавление ключа только в `ru-RU`, минуя `en-US`
- множественный ключ без части форм своего языка
- код отказа, оканчивающийся на `_one` или `_many`
- массовая правка словарей через `sed` без последующей проверки структуры JSON
- пустое значение `"ключ": ""`
