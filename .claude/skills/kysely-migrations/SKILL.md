# Миграции и слой данных

## Когда применять

Задача добавляет или меняет таблицу, колонку, индекс, ограничение. Либо добавляет запрос в репозиторий. Либо надо понять, откуда берутся типы базы.

## Расклад по файлам

| Что | Где |
|---|---|
| миграции | `apps/server/src/database/migrations/YYYYMMDDTHHMMSS-название.ts` |
| раннер | `apps/server/src/database/migrate.ts`, поверх `kysely-migration-cli` |
| сгенерированные типы | `apps/server/src/database/types/db.d.ts`, руками не править |
| сущности и производные типы | `apps/server/src/database/types/` |
| репозитории | `apps/server/src/database/repos/<домен>/` |
| пагинация | `apps/server/src/database/pagination/` |

Модуль базы глобальный, подключен `CamelCasePlugin`. В миграциях и SQL пишется змеиный регистр (`workspace_id`), в коде читается верблюжий (`workspaceId`).

## Порядок добавления изменения схемы

1. Создать файл миграции

```
pnpm --filter server migration:create <название-в-кебаб-кейсе>
```

Команда сама проставит временную метку в имени. Свою метку не выдумывать, порядок применения зависит от имени.

2. Написать `up` и `down`

`down` обязателен и должен действительно откатывать `up`.

Образец существующего стиля, `20260509T121236-labels.ts`

```ts
import { type Kysely, sql } from 'kysely';

export async function up(db: Kysely<any>): Promise<void> {
  await db.schema
    .createTable('labels')
    .addColumn('id', 'uuid', (col) =>
      col.primaryKey().defaultTo(sql`gen_uuid_v7()`),
    )
    .addColumn('name', 'varchar', (col) => col.notNull())
    .addColumn('workspace_id', 'uuid', (col) =>
      col.references('workspaces.id').onDelete('cascade').notNull(),
    )
    .addColumn('created_at', 'timestamptz', (col) =>
      col.notNull().defaultTo(sql`now()`),
    )
    .execute();

  await db.schema
    .createIndex('labels_workspace_id_type_name_unique')
    .on('labels')
    .columns(['workspace_id', 'type', 'name'])
    .unique()
    .execute();
}

export async function down(db: Kysely<any>): Promise<void> {
  await db.schema.dropTable('labels').execute();
}
```

Принятые в проекте соглашения

- первичный ключ `uuid` со значением по умолчанию `gen_uuid_v7()`
- временные метки `timestamptz` со значением по умолчанию `now()`
- принадлежность рабочему пространству через `workspace_id` с внешним ключом и `onDelete('cascade')`
- имя индекса вида `<таблица>_<колонки>_idx`, уникального `<таблица>_<колонки>_unique`
- на каждую колонку внешнего ключа, по которой идет выборка, свой индекс

3. Применить

```
pnpm --filter server migration:up
```

Разработческий сервер миграции сам не применяет. В продакшене они применяются при старте через `MigrationService.migrateToLatest()`.

4. Перегенерировать типы

```
pnpm --filter server migration:codegen
```

Команда читает базу по `DATABASE_URL` из корневого `.env` и переписывает `db.d.ts`. Без этого шага новые колонки не типизированы.

5. Обновить сущности в `apps/server/src/database/types/`, если добавлена таблица

## Жесткие правила

- существующая миграция не редактируется никогда. Даже если в ней ошибка, пишется новая
- `db.d.ts` не правится руками
- `migration:down` и `migration:reset` заблокированы хуком. Если откат действительно нужен, попросить пользователя выполнить вручную
- добавление `NOT NULL` в непустую таблицу делается в три шага: колонка с `NULL`, заполнение значений, установка ограничения
- удаление колонки отделяется от выкладки кода, который перестал ее читать

## Запросы

Запросы живут в репозиториях, не в сервисах. Сервис координирует несколько репозиториев и внешние эффекты.

Требования к новому запросу

- всегда ограничивать `workspaceId`, если данные принадлежат рабочему пространству
- для списков использовать существующий механизм пагинации, а не собственный `limit`
- фильтр прав применять до пагинации. Образец `PagePermissionRepo.userCanAccessPagePredicate` в `apps/server/src/database/repos/page/page-permission.repo.ts`, он собирает SQL-предикат, требующий доступ ко всем ограниченным предкам страницы
- атомарную операцию оборачивать в транзакцию. Сервис может внедрить `KyselyDB` через `@InjectKysely()` и провести несколько репозиториев внутри одной транзакции
- при потере доступа чистить связанные записи в той же транзакции: избранное, наблюдателей

## Проверка

```
pnpm --filter server test -- database
pnpm --filter server build
```

Плюс агент `schema-reviewer` в пункте 2 пост-скоуп ревью.

## Антипаттерны

- запрос в контроллере или в сервисе вместо репозитория
- выборка списка без ограничения по рабочему пространству
- проверка прав в приложении после того, как строки уже отобраны и обрезаны пагинацией
- новая колонка под секрет, которая хранится открытым текстом. Ключи провайдеров ИИ шифруются AES-256-GCM от `APP_SECRET`, наружу отдается только маскированный превью
- смена размерности вектора в `page_embeddings` без миграции и переиндексации. Сейчас размерность 1536
